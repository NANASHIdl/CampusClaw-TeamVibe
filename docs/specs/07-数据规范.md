# 数据规范 · CampusClaw · TeamVibe

适用：`backend/app/models/`（关系库）、`backend/migrations/`（Alembic）、`app/services/knowledge`（切片与向量）、`uploads/`（对象存储）
被谁读到：规则文件 `.cursor/rules/data.mdc`，globs `backend/app/models/**`、`backend/migrations/**`；技能 `skills/data-change/SKILL.md`
数据字典：`docs/data-dictionary.md`（唯一处）

---

## 1. 命名与类型

- 表名小写复数：`users`、`classes`、`memberships`、`materials`、`chunks`、`sessions`、`messages`、`ask_logs`。
- 主键 `id`：ULID 字符串 26 位（`CHAR(26)`），**不用自增整数**——跨存储引用时不暴露行数。
- 外键 `<单数表名>_id`；时间字段统一 UTC 存储，后缀 `_at`（`TIMESTAMPTZ`）。
- 状态用枚举并写清取值，落在 `CHECK` 约束里，不靠应用层保证：
  - `materials.status`：`pending` / `processing` / `ready` / `failed`
  - `messages.role`：`user` / `assistant`
  - `memberships.role`：`teacher` / `student`
- 本项目的核心字段 `class_id`：**除 `users`、`classes` 外所有业务表都带，且非空**。它是逐资源授权判定唯一可依赖的字段。

## 2. 审计字段

每张业务表带 `created_at`、`updated_at`、`created_by`（`users.id`，系统写入时为 `system`）。

- 软删用 `deleted_at`（`NULL` 表示未删），查询默认带 `deleted_at IS NULL`。
- 只增不改的表：`messages`、`ask_logs`；对它们的「修改」一律新增行。
- `updated_at` 由数据库触发器或 ORM `onupdate` 维护，不由业务代码手写。

## 3. 迁移纪律

- 迁移文件只增不改，路径 `backend/migrations/versions/`，文件名 `YYYYMMDDHHMM_<短横小写英文名>.py`。
- 每条迁移的 `downgrade()` 必须实现，不允许 `pass`；文件头注释写回滚动作一句话。
- 语句条件化可重跑（`op.execute("CREATE TABLE IF NOT EXISTS ...")` 或 Alembic 的 `checkfirst` 语义）。
- 结构变更先加后删：加字段 → 双写 → 切读 → 删旧字段；删字段的迁移必须晚于「切读」那次发布。
- **不得在应用启动时自动迁移**；迁移只在发布第 2 步执行（见 `docs/specs/05-部署运维规范.md` §6）。

**判据**：`alembic downgrade -1` 后 `alembic upgrade head` 能回到同一 schema（`alembic check` 无差异）。

## 4. 数据字典

`docs/data-dictionary.md` 是**唯一处**：每张表的用途、每个字段的含义、取值、是否敏感。结构变更必须同步该文件。

含义分散时，同一个字段会在不同模块出现不同解释（`status` 是最容易分裂的一个）。

**判据**：`make check` 的 `docs-lint` 校验 `models/` 中出现的表名与字段名在数据字典里都有条目，缺一条即失败。

## 5. 敏感数据分级

| 级别 | 例子 | 处理 |
| --- | --- | --- |
| 公开 | 帮助文案、错误码说明 | 可直接返回 |
| 内部 | 班级名称、资料标题、切片正文 | 本班可见；不进日志 |
| 敏感 | 资料原文附件、提问原文、会话内容 | 不进日志；接口只在「取正文」时返回；导出需脱敏 |
| 机密 | 口令哈希、会话令牌、`LLM_API_KEY` | 任何接口都不返回；日志中只允许出现「存在/不存在」 |

- 口令用 bcrypt（cost=12）存储；预置口令取自 `.env` 的 `SEED_*_PASSWORD`。
- 学生邮箱在导出与日志中做脱敏（`a***@pku.edu.cn`）。

## 6. 留存与删除

| 数据 | 留存期 | 到期动作 |
| --- | --- | --- |
| 提问会话与消息 | 一学期（约 18 周） | 归档后删除，`ask_logs` 保留聚合计数 |
| 提问日志 `ask_logs` | 一学年 | 删除 |
| 资料与切片 | 教师删除或班级结课 | 按 §7 副本清单删除 |
| 会话令牌 | 720 分钟 | 自动过期并清理 |
| 备份 | 30 天 | 轮转覆盖 |

**删除时的副本清单**（缺一项即为未完成删除）：

1. 业务库记录：`materials` 软删 → 7 天后硬删；`chunks` 随资料硬删；
2. 向量库：`campusclaw_chunks` 中 `material_id` 对应的点；
3. 对象存储：`uploads/<class_id>/<material_id>.<ext>` 原文件；
4. 缓存：检索结果缓存键 `search:<class_id>:*`；
5. 备份介质：在下一次全量备份轮转后自然消失（**在删除记录里写明这一条，不假装立即消失**）。

每学期执行一次删除演练，按清单逐项核对，记录用时。

**判据**：删除一条资料后，用其 `chunk_index` 在向量库检索不到；`uploads/` 下对应文件 404；备份中仍存在（预期，且已记录）。

## 7. 跨存储一致性

写入顺序（资料上传）：

```
1. 写 materials(status=pending) + 落 uploads/ 文件 → 同一事务外的两步，失败即整体失败
2. 提交后投递解析任务 → chunks 入库 → 向量入库 → materials.status=ready
任一步失败：materials.status=failed，保留原因，可由「重新上传」补偿
```

删除顺序相反：先软删业务记录并标记，再异步清理切片、向量与文件。

- 切片与向量是派生数据：以 `chunks` 表为准，向量库可整表重建（`deploy/rebuild-index.md`）。
- 一致性检查任务每周一次：比对 `chunks` 行数与向量库点数，差异 > 0 即告警。

**判据**：在「chunks 入库后、向量入库前」制造一次失败，检查 `materials.status=failed` 且有残留切片；重跑任务后残留被清理。

## 8. 测试数据

- 生产数据不进测试环境；需要样本时脱敏后导出。
- 测试用 A / B 两班预置数据（各 1 名教师、2 名学生、3 份资料），口令来自 `.env` 的 `SEED_*_PASSWORD`。
- 种子脚本 `backend/tests/seed.py` 幂等：重复执行不产生重复行（依赖唯一索引而非「先查再插」）。

## 违反时

结构变更未同步数据字典的，先补字典再合并；删除演练中出现未清理的副本，补进 §6 的清单并说明原因。
