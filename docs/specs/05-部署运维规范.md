# 部署运维规范 · CampusClaw · TeamVibe

适用：`Dockerfile.api`、`Dockerfile.web`、`docker-compose.yml`、`docker-compose.test.yml`、`deploy/`
被谁读到：规则文件 `.cursor/rules/ops.mdc`，globs `Dockerfile*`、`docker-compose*.yml`、`deploy/**`；技能 `skills/release/SKILL.md`

---

## 1. 可复现构建

- 两个 Dockerfile 都分阶段：
  - `Dockerfile.api`：`builder`（`python:3.12-slim`，按 `requirements.lock` 装依赖、`pip install --no-compile`）→ `runtime`（只拷 venv 与 `app/`，`USER 10001`，`--no-cache-dir`）；
  - `Dockerfile.web`：`builder`（`node:20-alpine`，`npm ci` 后 `npm run build`）→ `runtime`（`nginx:1.27-alpine`，只拷 `dist/` 与 `nginx.conf`）。
- 依赖锁定文件入库：`backend/requirements.lock`、`frontend/package-lock.json`；构建时用 `npm ci` / `pip install -r` 按锁定版本安装，**不用 `npm install`、不用不带版本的 `pip install`**。
- 镜像标签用提交号短 SHA 或版本号，**不用 `latest`**。同一提交号构建两次，`docker image inspect` 的 `Id` 应一致（依赖源可达时）。
- `.dockerignore` 排除 `.git/`、`.env`、`node_modules/`、`tests/reports/`、`uploads/`；**`.env` 不得进构建上下文**。

**判据**：`docker history --no-trunc <image> | grep -i secret` 无命中；`docker run --rm <image> env | grep -E "SESSION_SECRET|API_KEY"` 为空。

## 2. 环境与配置

| 环境 | 用途 | 入口 | 配置来源 |
| --- | --- | --- | --- |
| dev | 本机开发 | `docker compose up` | 本机 `.env` |
| test | 自动化测试 | `docker compose -f docker-compose.test.yml up` | `.env.test`（不含真实密钥，模型走替身） |
| prod | 部署验收 | `deploy/` | 部署机 `.env`（不进仓库） |

- **同一镜像跨环境，只换配置。** 各环境各构建一次时，测试结论不代表生产行为。
- `api` 与 `db`、`qdrant` 不映射宿主端口，对外入口只有 `web`（`WEB_PORT`，默认 8080）；`web` 反代 `/api/` 与 `/health` 到 `api:8000`。
- 容器时区固定 `TZ=UTC`；数据库时间统一 UTC 存储。

## 3. 健康检查与优雅停机

三个端点，全部免认证，返回结构一致：

```json
{ "status": "ok", "version": "0.0.1", "commit": "aed794d", "time": "2026-10-28T02:31:07Z",
  "deps": { "db": "up", "qdrant": "up", "llm": "up" } }
```

| 端点 | 语义 | 失败时 |
| --- | --- | --- |
| `GET /health/live` | 进程存活 | 不查依赖，永远 200（除非进程死了） |
| `GET /health/ready` | 可以接流量 | 任一依赖 `down` → 503 |
| `GET /health` | 综合体检（含版本、依赖明细） | 任一依赖 `down` → 503，**进程不退出** |

- 依赖探测各带 2 秒超时；`llm` 只做 TCP/HTTP 可达性检查，**不发起计费调用**。
- 优雅停机：收到 `SIGTERM` 后停止接新连接，等在途请求完成，上限 30 秒（`uvicorn --timeout-graceful-shutdown 30`），超时后强退并记 `event=shutdown_forced`。
- compose 的 `healthcheck` 打 `/health/ready`，`depends_on: condition: service_healthy`。

**判据**：`docker compose stop qdrant` 后，`/health` 返回 503 且 `deps.qdrant=down`，`api` 容器仍 `Up`；`docker compose restart api` 期间无 502 堆积（在途请求被处理完）。

## 4. 结构化日志与指标

单行一条 JSON，字段固定（`core/logging.py` 产出）：

```json
{"ts":"2026-10-28T02:31:07.412Z","level":"info","module":"retrieval","request_id":"01HQ7Z3K9V2M4T8R6B1C0X5DNP","class_id":"01HQ...","user_id":"01HQ...","event":"search_done","mode":"hybrid","hits":3,"latency_ms":182}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `ts` | ✅ | ISO8601，UTC，毫秒 |
| `level` | ✅ | `debug` / `info` / `warn` / `error` |
| `module` | ✅ | 分层名：`api` / `services` / `repositories` / `integrations` |
| `request_id` | ✅ | 与响应头 `X-Request-ID` 一致，ULID 26 位 |
| `event` | ✅ | 下划线短名：`search_done`、`upload_rejected`、`outbound_blocked` |
| `latency_ms` | 视事件 | 整数毫秒 |
| `error_code` | 错误时必填 | 与响应 `code` 一致 |
| `class_id` / `user_id` | 视事件 | 内部 ID，非邮箱 |

**不得落日志**：会话令牌原值、口令原文、资料正文、学生提问原文（只记长度与 SHA256 前 8 位）、模型提示词全文。

指标至少四项，超出即告警：

| 指标 | 阈值 | 责任人 | 处置动作 |
| --- | --- | --- | --- |
| 5xx 比例（5 分钟窗） | > 2% | 后端值班 | 看 `error_code` 分布，先判依赖还是代码 |
| `POST /sessions/{id}/messages` P95 | > 12s | 后端值班 | 查 `latency_ms` 分段（检索 / 生成），必要时降级关键词模式 |
| 依赖连通（db / qdrant） | 连续 3 次探测失败 | 运维值班 | 先看 `/health`，再重启对应容器 |
| 上传失败率 | > 10% | 后端值班 | 看 `upload_rejected` 的原因分布 |

**判据**：抽样一次提问请求，用同一个 `request_id` 在 `api`、`services`、`integrations` 三处日志都能检索到。

## 5. 发布与回滚

发布顺序（写成技能 `skills/release/SKILL.md`，不口头交接）：

1. 构建镜像，以提交号短 SHA 打标签；
2. 执行迁移（先加后删，向后兼容；见 §6）；
3. 滚动或蓝绿发布，先起新实例；
4. `/health/ready` 通过后接流量；
5. 打版本标签（`v0.0.1-skeleton` 形式），写 `docs/changes/<变更名>.md` 记录版本与验证结论。

回滚只有一条分支：**回到上一个版本标签对应的镜像**，不回滚数据（迁移已保证向后兼容）。

- 回滚命令固定：`IMAGE_TAG=<上一个SHA> docker compose up -d --no-deps api`；
- 每个迭代演练一次回滚并记录耗时到 `docs/changes/`；**未演练过的回滚不算可用**。

## 6. 数据变更顺序

`加字段 → 双写 → 切读 → 删旧字段`。删除类操作放在最后，且旧版本代码在新结构上仍可运行。

- 迁移由 Alembic 管理，`alembic upgrade head` 在发布第 2 步执行，**不在应用启动时自动迁移**。
- 每个迁移文件头写回滚动作（`downgrade()` 必须实现，不允许 `pass`）。
- 迁移只增不改：已合并的迁移文件不得修改。

## 7. 备份与恢复

| 项 | 值 |
| --- | --- |
| 备份对象 | PostgreSQL（业务数据）、`uploads/`（原始附件）、Qdrant 快照（可重建，优先级最低） |
| 频率 | 每日 02:00 全量 `pg_dump -Fc` + WAL 归档（连续） |
| 保留期 | 全量 30 天，WAL 7 天 |
| RPO | 15 分钟 |
| RTO | 2 小时 |
| 演练 | 每学期一次恢复演练，记录用时到 `docs/changes/` |

未演练过的备份不作为恢复依据。Qdrant 数据可从 PostgreSQL 的 `chunks` 表重建，重建脚本写在 `deploy/rebuild-index.md`。

## 8. 发布留痕

每次发布在 `docs/changes/YYYY-MM-DD-<变更名>.md` 记录：版本号、包含变更、门禁结果、健康检查结果、回滚演练耗时。按版本标签应能检索到对应记录。

## 违反时

发布相关改动需人工复核：回滚能力或健康检查结果发生变化时，先在 test 环境演练一次再进 prod。
