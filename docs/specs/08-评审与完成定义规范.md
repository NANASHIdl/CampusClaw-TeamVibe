# 评审与完成定义规范 · CampusClaw · TeamVibe

适用：全部变更；核心两条（门禁、提交与评审）常驻在 `AGENTS.md` §2 §3，每次会话都会读到
被谁读到：`AGENTS.md` §2 §3 + 技能 `skills/review-change/SKILL.md`

---

## 1. 完成定义（Definition of Done）

一条变更在**同时**满足下列六条后才算完成：

1. 规约里列出的 Scenario 全部满足，每条读写资源的 Requirement 都配了越权失败用例；
2. `make check` 全绿（14 个子项，见 §5）；
3. 涉及提示词或模型版本改动时，评测集已跑过（20/20）并归档到 `docs/eval/`；
4. 文档同步：`README.md`、`docs/data-dictionary.md`、`docs/specs/01-产品设计规范.md` 的页面清单随改动更新；
5. 验证记录归档到 `docs/changes/<变更名>.md`，含门禁结果与健康检查结果；
6. 另一名成员在自己机器上从零跑通（`clone → .env → 一条命令 → /health`）。

**判据**：逐条打勾，勾不上的那一条就是未完成的部分——不是「差不多完成」。

## 2. 变更规模上限

- 单次变更不超过 `tasks.md` 里的一组任务（例如「第 4 组：骨架」）。
- 单次变更的 diff 上限：`backend/` 与 `frontend/` 合计 ≤ 600 行（不含锁文件与迁移）。超出即拆分。
- 规模越大，评审越趋近于走过场——上限是为了让评审有效，不是为了好看。

## 3. 评审检查表

| 谁来审 | 看什么 | 判据 |
| --- | --- | --- |
| 人（组长或轮值评审人） | 规约覆盖：Scenario 是否真正满足，而不是「接口通了」 | 逐条对照 spec，缺一条打回 |
| 人 | 授权判定：跨班是否按 404 处理，响应是否与「不存在」一致 | 互换 ID 重放，响应除 `request_id` 外逐字节相同 |
| 人 | 数据迁移：是否可回滚，是否先加后删 | `alembic downgrade -1` 能执行 |
| 人 | 提示词改动：是否跑过评测，模板版本号是否 +1 | `docs/eval/` 有对应记录 |
| 人 | 例外：是否书面化并写明失效条件 | §6 |
| Harness（助手自审） | 分层与依赖方向、命名、错误码登记、重复代码 | `make check` 的 `layout` / `api-lint` |
| 格式化工具 | 代码风格 | `fmt-check`，不占用评审时间 |

评审意见只提「规约不符」与「判据缺失」，不提个人风格偏好；风格问题交给工具。

## 4. 责任人与时限

- 每次变更在 `proposal.md` 头部指定一名评审人（不与作者同一人）。
- 评审请求在一个工作日内响应；超期由提出者升级到组内例会，**而不是自行合并**。
- 主干保护：`main` 禁止直接 push，要求 1 名评审人 + `make check` 绿 + 分支与最新 `main` 同步。

## 5. 门禁必跑

```bash
make check
# api-lint api-types api-test api-migrate web-lint web-types web-test e2e
# fmt-check layout secret-scan spec-validate docs-lint gate-tamper
```

| 子项 | 检查什么 | 失败含义 |
| --- | --- | --- |
| `api-lint` | `ruff check backend` | 未使用导入、裸 `except`、`print` |
| `api-types` | `mypy backend/app` | 类型不一致 |
| `api-test` | `pytest -q backend/tests` | 用例失败或跳过数增长 |
| `api-migrate` | `alembic check` + `downgrade -1` / `upgrade head` 往返 | 迁移不可回滚或与模型不一致 |
| `web-lint` | `eslint frontend/src` | 未使用变量、`v-html` 违规 |
| `web-types` | `vue-tsc --noEmit` | 类型错误 |
| `web-test` | `vitest run` | 组件测试失败 |
| `e2e` | `playwright test` | 主路径断裂 |
| `fmt-check` | `ruff format --check` + `prettier --check` | 格式不一致 |
| `layout` | 分层 import 图、路由准入声明、表名字段是否在数据字典 | 反向依赖或未声明准入 |
| `secret-scan` | `gitleaks detect --no-git -v` | 明文密钥 |
| `spec-validate` | `openspec validate <变更名> --strict` | 四份文件不全或 Requirement 缺 Scenario |
| `docs-lint` | 八份规范文件存在、章节齐、术语表与页面清单可解析 | 规范缺章节 |
| `gate-tamper` | `Makefile`、`.githooks/`、`AGENTS.md`、`.cursor/rules/` 摘要比对 | 门禁被放宽 |

- **不得为了让门禁变绿而放宽其中的检查或删断言**，也不得跳过本地提交钩子（`git commit --no-verify` 视为违规）。
- 骨架落地前只有 `spec-validate` / `docs-lint` / `secret-scan` / `layout` 可跑：用 `make check-docs`，并在验证记录里写明其余子项「待骨架落地」。

## 6. 例外书面化

确有理由保留旧写法时，把例外写进对应规范文件的「例外」小节，注明：理由、失效条件、复核日期。

```
## 例外
- E-01 2026-10-28 起 `materials.title` 允许 200 字符（原 120），
  理由：教务导出标题偏长；失效条件：导入功能上线后复核；复核日期 2026-11-30。
```

留在会话里的口头豁免无效。例外超过 3 条时，说明规范本身需要修订。

## 7. 证据归档

变更说明、验证记录、评审结论归档到 `docs/changes/<变更名>.md`，按变更名可一次检索到三份材料。

提交信息尾部写三个字段，值必须查得到（指向的文件存在、命令跑得出）：

```
Change: 2026-10-28-bootstrap-skeleton
Verify: make check-docs
Evidence: docs/changes/2026-10-28-bootstrap-skeleton.md
```

正文写清「改了什么、依据哪条规约」（引用 `docs/specs/` 的章节号或 spec 的 Scenario 编号）。

## 8. 改这些文件要人审

`AGENTS.md`、`CLAUDE.md`、`.cursor/`、`.githooks/`、`openspec/`、`Makefile`、`scripts/`、`.github/`、`docs/specs/`。

改它们的变更要在说明里写清：改了什么、为什么、怎么验证。**助手不得自行放宽其中的检查**，也不得为了让某次实现通过而改判据。

## 违反时

先判定是「流程没走」还是「判定不清」：前者退回补流程；后者改本文件并记入变更说明，同时检查是否有其他规范需要跟着改。
